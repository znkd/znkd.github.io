挤压

挤压 大家好，今天想和大家聊聊一个比较现实的话题——应用工程师的生存空间。 我说的"应用工程师"，指的是那些既不是搞算法的、也不是做数据业务的、更不是对某个业务领域特别精通的人。简单来说，就是写业务代码的、做Web开发的、做客户端的、做后台服务的……我们姑且叫自己"中间层工程师"。 但大家会发现，这两年大家的生存空间确实在被挤压。 挤压从何而来 先说几个数据： 岗位数量的变化 根据工信部发布的《互联网和相关服务业年度统计数据报告》，中国互联网及相关服务业从业人数在2022年达到峰值327.1万人，到2023年下降到293.3万人，一年就少了30多万人。猎聘的数据显示，2025年Q1互联网行业程序员岗位需求同比下降23%，而求职者数量却增加了17%。 初级岗位的收缩 斯坦福大学的研究表明，自2022年底至2025年7月，22至25岁年轻程序员就业人数累计减少近20%。入门级编程工作岗位减少了32%-35%。 薪资的分化 2025年程序员平均薪资涨幅从2020年的25%跌到5.3%，初级岗位薪资普遍下调10-15%。但另一边，大模型算法工程师年薪高达50万-200万元，AI开发类岗位薪资达到1.1万-1.7万/月。 这些数据说明了一个残酷的事实：市场正在发生结构性变化。 为什么会这样 我认为主要有三个原因： 1. AI工具的普及 GitHub Copilot、通义灵码等AI编程工具已经能完成相当一部分高级代码编写，不仅能写基础CRUD，还能进行代码补全、重构、调试，甚至能根据自然语言描述生成完整功能模块。某银行技术团队通过部署AI编码助手，将基础模块开发效率提升300%，同时减少50%的初级程序员需求。硅谷科技大厂的程序员们每天喝咖啡的时间增加了，因为谷歌已披露20%左右的代码由AI编写。扎克伯格更预测，到2025年，“AI将达到中级软件工程师的编程水平”。 2. 企业从扩张转向收缩 互联网人口红利见顶，资本投资趋于谨慎。企业更倾向于"优化存量"而非"扩张增量"。更夸张的是初创企业就业蓄水池的严重萎缩——国内获得融资的初创企业数量从2018年的5.1万家骤降至2024年的110家，融资总额从5000亿元缩水至不足100亿元。 3. 技能折旧加速 大模型技术重构开发流程，传统CRUD开发需求锐减。低代码/无代码平台普及，基础开发岗位价值下降。技术栈更新周期从3-5年缩短至1-2年。 应用工程师的出路 那我们这些"中间层"该怎么办？我分享三个方向： 1. 向业务纵深 成为对某个业务领域特别了解的人。技术只是手段，业务才是目的。你要解决的问题是"如何用技术推动业务"，而不是"如何写代码"。同样是做支付系统，懂得支付业务、风控、资金清算的人，比只会写CRUD的人更有价值。 2. 向技术深度 在架构设计、系统优化、基础设施这些层面建立壁垒。初级CRUD可以被AI替代，但系统架构、性能优化、复杂问题排查这些需要大量经验积累的领域，AI还差得远。2024年嵌入式开发岗位因工业互联网、汽车电子需求增长，薪资稳定性就很强。 3. 向跨界能力 技术+产品、技术+管理、技术+销售……复合型人才在這個时代更吃香。因为技术壁垒在降低，但理解技术、又能和其他领域结合的人，反而变得稀缺。 利好与不利 不利因素： 初级岗位持续收缩，35岁危机在提前 企业要求"即插即用"，培养成本敏感 竞争加剧，不仅要和应届生竞争，还要和被裁的资深工程师竞争 利好因素： 传统行业数字化转型仍在进行，需要大量应用层人才 新基建（智算中心、人形机器人等）带来新机会 AI虽然替代了部分工作，但也降低了创业的门槛 结语 写到这里，我想说，AI确实在改变程序员的工作方式，但它目前主要替代的是"可重复的、规则明确的"工作。真正需要创造力、经验积累、人际沟通的岗位，AI还难以触及。 与其焦虑被AI替代，不如把AI变成自己的工具。毕竟，马车车夫不会因为汽车出现而全部失业，他们中的一部分人学会了开车。 大家有什么想法，欢迎评论区聊聊。 数据来源： 工信部《互联网和相关服务业年度统计数据报告》 猎聘数据（2025年Q1） 斯坦福大学研究（2022-2025） JienDa《2025年应届程序员就业报告》 黑马程序员2025就业数据

Essay on Codex Desktop

一次关于 Codex 桌面版与 MCP 接入方式的技术随笔 最近抽时间体验了一下 Codex 的 macOS 桌面版（Version 260204.1342 (531)。 作为一次“并非带着明确目标”的尝试，结果反而有些出乎意料。 最先让我产生兴趣的，是 Codex 对 Git worktree 的原生支持。 它并不试图用某种抽象的方式“替代开发流程”，而是非常直接地承认一个事实：在真实的工程环境中，我们经常需要在同一个仓库里，同时处理多个 Bug、Feature，甚至实验性改动。 通过 worktree 并行推进这些修改，Codex 给人的感觉更像是一个理解真实研发节奏的工具，而不是停留在“单任务理想状态”的开发助手。 真正的挑战，出现在 MCP（Model Context Protocol）的配置阶段。 起初，我沿用了此前接入第三方服务时最常见的方式： 配置 API Key + 服务 URL，然后进行连接校验。 结果并不复杂，也不意外——失败。 接下来是一段典型却略显漫长的排查过程： 反复确认 Key 是否正确、参数是否遗漏，重启客户端，再次检测。 结果始终一致：连接失败，没有明显的方向性提示。 直到后来，在朋友的提醒下，我开始怀疑问题并不在“参数是否填对”，而在于 接入方式本身是否成立。 转而尝试使用 STDIO 方式时，Codex 给出了一个非常明确、但之前被我忽略的信息： 远程 MCP 服务必须使用 Streamable HTTP 这句话本身不复杂，却瞬间澄清了很多误解。 它意味着： STDIO 仅适用于本地 MCP 服务 一旦 MCP 运行在远程环境，通信模型就必须基于 HTTP 鉴权方式（API Key 或 Bearer Token）也随之成为不可回避的问题 到这里，问题不再是“我哪里配错了”，而是“我是否选对了通信模型”。 在后续的讨论与资料查阅中，我们逐渐把 MCP 的接入方式整理成了一个更清晰的结构： ...
